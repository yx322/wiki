# Iceberg 表存储架构

## 📊 Iceberg 表存储架构

```
metadata.json            ← 记录快照（Snapshot）与 manifest-list 路由
  ↓
manifest-list            ← 存储 10 个 manifest 文件的元数据（包含分区范围统计）
  ↓
manifest-1 ~ manifest-10 ← 存储 26.9 万个数据文件的绝对路径、分区键值及列级 Min/Max 统计
  ↓
data-1.parquet ~ data-268969.parquet ← 散落在对象存储中的实际数据文件
```

| 指标 | 数值 |
|------|------|

## 🔍 为什么查询时必须首先解构元数据？

### 解决无索引对象存储的文件定位问题

对象存储（如 S3、OSS）本质是键值对存储，缺乏传统数据库的物理文件索引。Iceberg 必须依赖元数据作为指针，建立"特定用户 ID → 特定 Parquet 文件路径"的确定性映射。

### 驱动内存级分区裁剪（Partition Pruning）与下推过滤

引擎在内存中解析清单文件（Manifest），根据查询条件（如 `WHERE task_empId = 103400`）求值。通过静态分区边界和列级 Min/Max 统计，在排除无关文件后，仅针对命中目标的文件对象发起网络请求。

---

## ⚠️ 双分区（过度分区 Over-partitioning）引发的性能坍塌

190 万行的总数据量在标准大数据场景下，本应由 1 至 2 个常规 Parquet 文件（标准大小通常为 128MB - 512MB）完整承载。

当其被双分区（如：时间 + 员工 ID）极度切碎为 13.6 万个分区时，导致文件 Footer（页脚元数据）的体积远超实际数据载荷，直接引发以下双重性能瓶颈：

### 瓶颈一：元数据检索阶段的 CPU 算力枯竭（扫描慢）

**元数据膨胀**：由于要记录 26.9 万个文件的详细统计信息，这 10 个 Manifest 文件的物理体积和数据结构极度臃肿。

**单线程解析限制**：PyIceberg 作为轻量级 Python 客户端，采用单线程在内存中反序列化并解析这 26.9 万条元数据。在发起任何实际的数据下载请求之前，光是执行表达式匹配和过滤计算，就会在客户端造成长达数秒甚至十几秒的 CPU 阻塞。

### 瓶颈二：数据提取阶段的网络 I/O 频繁握手（下载慢）

**HTTP 并发开销放大**：即使经过严格的分区裁剪，查询单个用户仍可能需要从不同分区提取几十个极小文件。

**RTT 延迟叠加**：每个几 KB 的 Parquet 文件都需要一次独立的 HTTP GET 请求。针对对象存储的高频并发请求会带来巨大的 TCP 握手和 TLS 握手开销。这种高频次、低载荷的网络往返时延（RTT）累加，是导致最终查询耗时飙升的主因。

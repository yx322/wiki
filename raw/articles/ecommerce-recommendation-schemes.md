对于你的商品推荐场景，想要在 RRF 混合检索的基础上融入销量、库存、主推等业务因素，有两种主流的设计思路：**加权 RRF** 和 **两阶段排序（RRF + 重排序）**。

根据你的需求，我推荐**方案一**，因为它与向量检索 + 全文检索的 RRF 框架天然契合，实现起来也相对简洁。

### 📊 设计思路对比
在深入细节前，你可以先对两种方案有一个整体的了解：

| 设计思路 | 核心原理 | **优点** | **缺点** |
| :--- | :--- | :--- | :--- |
| **方案一：加权 RRF** | 将销量、主推等因素作为独立的**检索器**，与语义、关键词检索并列，通过 RRF 算法进行融合加权。 | 1. **结构清晰，理念一致**：符合“多路召回，融合排序”的顶层设计；<br>2. **公平归一化**：RRF 基于排名而非原始分数，避免了销量、相似度等不同量纲数值难以直接相加的问题。 | 无法处理销量排名相差一位但销量绝对值相差巨大的情况，即在平滑排名的同时，也抹平了极端差异。 |
| **方案二：两阶段排序 (RRF + 重排)** | 先通过 RRF 获取一个**语义和关键词**都相关的商品候选集，然后在这个小集合上，用复杂的业务公式进行一次**最终排序**。 | 1. **灵活性强**：可自由组合销量、库存、价格等各种因子，设计复杂的业务公式；<br>2. **计算高效**：重排序只在 RRF 输出的少数商品上进行，开销小。 | 1. **可能存在“漏掉”好商品**：如果某个商品销量极高但文本和语义都完全不相关，它可能在第一阶段就被排除了；<br>2. **两阶段分离**：需要两次计算。 |

### ✅ 推荐方案一：加权 RRF（你的场景首选）

加权 RRF 是现代搜索引擎（如 Elasticsearch、Azure AI Search）中解决此类问题的标准模式[citation:8]。它通过将你关心的每个因素都转化为一个“检索器”，让它们在同一套 RRF 框架下“讨论”，谁的综合排名更高，谁就胜出。

#### 核心思想：把业务因素都变成“检索器”
你不是在计算一个复杂的公式，而是在融合多个“排名专家”的意见。

1.  **语义专家**：向量检索，负责理解“舒适的运动鞋”和“适合跑步的鞋”在意思上是相近的。
2.  **关键词专家**：全文检索，确保用户搜“SN12345”时能精确匹配到对应的商品。
3.  **销量专家**：一个特殊的检索器，它的职责就是根据销量对商品进行排名[citation:8]。
4.  **主推专家**：根据商品是否主推来排名。你可以让主推商品都排在第1位，非主推商品排在一个靠后的固定位置[citation:8]。

最后，给不同的“专家”分配不同的**权重（Weight）**，表示他们的意见有多重要[citation:1][citation:8]。

#### 具体实现伪代码（以 Elasticsearch 为例）

目前主流的数据库和搜索引擎大多已支持此模式[citation:2][!citation:3][citation:5]。

```json
GET /your-goods-index/_search
{
  "retriever": {
    "rrf": {  // 倒数排名融合
      "retrievers": [ // 这是所有参与决策的“专家”
        {
          "standard": { // 专家1：关键词匹配（BM25）
            "query": {
              "match": { "goods_name": "3m口罩" }
            }
          },
          "weight": 0.3 // 权重30%
        },
        {
          "knn": { // 专家2：语义匹配（向量）
            "field": "embedding_dashscope",
            "query_vector": [0.1, 0.2, ...],
            "k": 50
          },
          "weight": 0.3 // 权重30%
        },
        {
          // 专家3：销量排序（业务规则）
          // 注意：这需要你的数据源支持简单的排序查询
          "standard": {
            "query": {
              "match_all": {}
            },
            "sort": [{ "sales_amount": "desc" }] 
          },
          "weight": 0.3 // 权重30%
        },
        {
          // 专家4：主推商品（业务规则）
          // 为所有主推商品创建一个常数排名，例如都排第一
          // 这通常需要一些技巧或数据预处理，但思想是将其作为一路独立的信号源
          "standard": {
            "query": {
              "term": { "is_ai_recomm": true }
            }
          },
          "weight": 0.1 // 权重10%
        }
      ],
      "rank_constant": 60 // 平滑因子，默认60即可
    }
  },
  "size": 10
}
```

#### 库存因素怎么加？
库存情况不太适合直接作为一个**排名信号**，它更像一个**强制过滤器**。逻辑上讲，一个缺货的商品不应该出现在推荐列表里。因此，**建议将 `stock_qty > 0` 作为所有查询的过滤条件**，而不是参与排名计分，这在逻辑和性能上都是最好的选择。

### 🧠 备选方案二：两阶段排序（RRF + 重排序）

如果你的业务规则非常复杂（比如销量前10名和11-20名要有巨大的分数落差），不希望被 RRF 平滑掉，可以采用此方案。

#### 第一阶段：混合召回
使用传统的 RRF，只融合**文本搜索**和**向量搜索**，从全量商品中快速筛选出前 N 个（例如 200 个）候选商品[citation:7]。

#### 第二阶段：精细化重排序
在你的应用代码（如 Python）中，拿到这 200 个候选商品后，再对你关心的销量、主推、价格等因素进行加权计算，进行最终排序。

**优点：**
*   **控制力强**：公式完全由你定义，例如：`最终分 = RRF分 * (1 + log(销量+1)*0.1 + 主推加分)`。
*   **逻辑简单**：对召回集进行二次计算的逻辑非常直观，易于调试和调整。

### 💎 总结与建议

对于你的商品推荐场景，我的建议是：

*   **首选方案一（加权 RRF）**。它与你的技术栈最契合，逻辑清晰，是搜索引擎官方推荐的做法[citation:8]。你只需要把销量和主推也看作是一路“检索”结果，交给 RRF 统一排序即可。
*   **库存处理**：直接用 `WHERE stock_qty > 0` 作为过滤条件，不要参与计分。
*   **权重调优建议**：
    *   **语义/文本主导**：如果推荐**相关性**很重要，可给向量、关键词检索器各分配 `0.35`，销量 `0.3`。
    *   **销量主导**：如果想推爆款，可给销量检索器分配 `0.6`，语义和关键词各 `0.2`[citation:2]。
    *   **避免过犹不及**：销量和主推的权重总和建议不超过 0.5，以保证推荐的“相关性”底线。

记住，RRF 的精髓在于融合**排名**而非分数，这样可以优雅地解决销量“7”和相似度“0.85”无法直接相加的问题[citation:1][citation:5]。

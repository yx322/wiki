# 湖仓一体化性能重构落地方案

## 一、核心痛点与重构目标

### 写入痛点
高频增量同步（17~150条）时，`table.overwrite` 在 Copy-on-Write 模式下引发严重写放大，且频繁触发 `CommitFailedException` 冲突锁死，耗时高达 **45 秒**。

### 查询痛点
下游 DuckDB 查询时，PyIceberg 每次都必须将 **190 万行**全表数据（~50MB）跨网络下载并全量加载到 Python 内存中，造成 **8.6 秒**的硬性网络和 CPU 搬运阻塞。

### 优化目标
- 写入降至 **20毫秒**
- 最新数据查询降至 **10毫秒秒开**
- 100% 消灭 Commit 冲突与 OOM 隐患

---

## 二、架构整体分工与数据流拓扑

本方案采用标准的 **"流数据库缓存（仓） + 湖格式长周期归档（湖）"** 湖仓一体架构：

### 🚀 终极方案（模式A：MySQL CDC，完全消灭接口与Python）

```
【源头：OA 业务系统的数据库 (MySQL)】
       │ 
       ▼ (RisingWave CDC 引擎通过 binlog 物理日志，毫秒级无感、流式捕捉每一次待办变动)
【实时核心：RisingWave 基础表 (Table)】 ──► 内部自动 Upsert（写入耗时：0秒，无需任何代码）
       │ 
       ▼ (RisingWave Iceberg Sink 模块自动在后台每 2 分钟大批次合并落湖)
【资产归档：阿里云 OSS Tables (冰湖表)】 ◄─── (在后台优雅、健康地自动更新去重)
```

**在这个终极状态下：**
- **接口（API）**：停用！再也不用担心接口网络超时、接口限流或者接口改版报错
- **Python 同步代码与定时器**：直接删除！零代码维护，不需要再写任何一行 Python 代码

### 🛠️ 过渡方案（模式B：Python 拉取接口）

```
【数据源头：OA 系统】
       │ 
       ▼ (模式 B: Python 定时拉取接口)
【写入第一站：RisingWave 内部物理表】 (写入耗时：20毫秒)
       │ 
       ▼ (RisingWave 流引擎：在内存中毫秒级执行增量去重计算)
【实时核心：RisingWave 物化视图】 ◄─── (下游高频实时查询直连此视图，10毫秒秒开)
       │ 
       ▼ (RisingWave Iceberg Sink：自动在后台每 2 分钟大批次打包落湖)
【资产归档：阿里云 OSS Tables (完全不分区表)】 ◄─── (仅用于跨年大历史报表深度分析)
```

## 三、RisingWave 核心配置 SQL 脚本（传送带搭建）

### 🔥 模式 A（终极方案：MySQL CDC，完全消灭接口与Python）

如果可以直接监控业务数据库的日志（binlog），就完全不需要接口了！接口可以直接光荣退役。

#### 为什么 CDC 模式不需要"去重视图"？

数据库的 binlog 日志带有极其严格的"动作原语（Action）"：
- **INSERT 信号**：当 OA 系统里新增一个待办
- **UPDATE 信号**：当员工完成了这个待办，binlog 会极其精准地发出 UPDATE 信号，包含旧值和最新修改的新值

RisingWave 的 CDC 引擎在收到 binlog 的 UPDATE 信号的那一毫秒，会自动把内存里原先那条旧状态直接抹掉改写为最新状态。

**结论**：数据在流进 RisingWave 的那一瞬间，它在物理表内部天生就已经处于最新、最干净、完全去重、跟源头数据库 100% 绝对同步的状态了！根本不需要再多此一举去建什么窗口函数视图。

#### 前置准备：MySQL 端配置

```sql
-- 确认 binlog 已开启
SHOW VARIABLES LIKE 'log_bin';          -- 必须是 ON
SHOW VARIABLES LIKE 'binlog_format';    -- 必须是 ROW

-- 创建 CDC 只读账号
CREATE USER 'rw_cdc_user'@'%' IDENTIFIED BY 'your_password';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'rw_cdc_user'@'%';
FLUSH PRIVILEGES;
```

#### RisingWave SQL（只需两句）

**第一步：开启 CDC 传送带，直接毫秒级流式同步源头业务表**

运行这句 SQL 的瞬间，RisingWave 会自动把 MySQL 里现存的 190 万条历史数据全量秒级同步进来，随后自动无缝切换到实时监听 binlog 状态。

```sql
CREATE TABLE source_todo_table (
    task_id VARCHAR PRIMARY KEY,  -- 待办任务主键 ID
    task_empId VARCHAR,           -- 员工 ID
    sync_time TIMESTAMP,          -- 时间戳
    status VARCHAR
) WITH (
    connector = 'mysql-cdc',       -- 核心：激活 RisingWave 原生 MySQL CDC 引擎
    hostname = 'oa_mysql_host',   -- 替换为 OA 系统的业务数据库 IP
    port = '3306',
    username = 'rw_cdc_user',     -- 业务数据库分配的只读 CDC 账号
    password = 'your_password',
    database.name = 'oa_biz_db',
    table.name = 't_todo_list'    -- 业务系统真正的源头表名
);
```

> 请谨慎使用此类代码。

**第二步：直接在基础表上插管子（Sink），自动异步写入阿里云 OSS Tables**

由于基础表现在天生就是干净去重的最终态，落湖的管子直接接在表上就行，让 RisingWave 在后台自动每 2 分钟大批次合并打包成 Parquet 文件提交给冰湖：

```sql
CREATE SINK iceberg_sink_to_oss 
FROM source_todo_table -- 🚀 终极简化：不需要视图了，直接接在 CDC 基础表上！
WITH (
    connector = 'iceberg',
    type = 'upsert',                        -- 走 Upsert 覆盖更新语义
    catalog.type = 'rest',                  -- 阿里云 REST Catalog
    catalog.uri = 'your_catalog_endpoint',
    warehouse = 'oss://your-bucket/path/',   -- 你的完全不分区冰湖表路径
    database.name = 'your_db',
    table.name = 'your_table'
);
```

> 请谨慎使用此类代码。

### 🛠️ 模式 B（过渡方案：Python 拉取接口）

如果只能拿接口，则保留 Python 调度器，RisingWave 纯作为高性能接收器。

#### RisingWave SQL（需要三步）

**第一步：创建承接源头数据的内部表**

```sql
CREATE TABLE source_todo_table (
    task_id VARCHAR PRIMARY KEY,
    task_empId VARCHAR,
    sync_time TIMESTAMP,
    status VARCHAR
);
```

> 请谨慎使用此类代码。

**第二步：创建"与接口逻辑一致的干净视图"（实时流式去重）**

RisingWave 会在内存中死死盯着上面的基础表。每当有新数据流入，该物化视图在内存中会自动增量计算更新，永远保持全量 190 万行最新、完全去重的最终待办状态：

```sql
CREATE MATERIALIZED VIEW mv_interface_clean_view AS
SELECT * EXCLUDE (rn) FROM (
    SELECT *, 
           ROW_NUMBER() OVER(PARTITION BY task_id ORDER BY sync_time DESC) as rn
    FROM source_todo_table
) WHERE rn = 1;
```

> 请谨慎使用此类代码。

**第三步：创建落湖管子（Sink），自动异步同步至阿里云 OSS Tables**

外流管道直接监听上面已经清洗去重的 `mv_interface_clean_view` 视图，它在后台作为一个高级缓冲代理，每隔 2~3 分钟大批次合并打包成高质量的 Parquet 文件，原子提交给完全不分区的冰湖表，物理斩断乐观锁冲突：

```sql
CREATE SINK iceberg_sink_to_oss 
FROM mv_interface_clean_view -- 接在去重干净视图上
WITH (
    connector = 'iceberg',
    type = 'upsert',                        -- 走自动 Upsert 覆盖更新语义
    catalog.type = 'rest',                  -- 对应阿里云 REST Catalog 体系
    catalog.uri = 'your_catalog_endpoint',   -- 阿里云 REST 服务 URL
    catalog.credential = 'your_credential', 
    warehouse = 'oss://your-bucket/path/',   -- 你的完全不分区冰湖表物理存储路径
    database.name = 'your_db',
    table.name = 'your_table'
);
```

> 请谨慎使用此类代码。

## 四、写入端与查询端代码改动清单

### 1. 【写入端】Python 同步脚本改造（仅针对模式 B）

彻底抛弃笨重的 `pyiceberg.overwrite`，每次拉回增量数据后，改用标准 PostgreSQL 协议（RisingWave 原生兼容）执行最纯粹的盲插追加（INSERT）：

```python
import psycopg2
import pandas as pd

# 1. 极速向 RisingWave 索要 max(sync_time) [内存查询，只需 1 毫秒]
conn = psycopg2.connect(host="your_risingwave_host", port=4566, user="root", database="dev")
with conn.cursor() as cur:
    cur.execute("SELECT max(sync_time) FROM source_todo_table;")
    max_sync_time = cur.fetchone()[0]

# 2. Python 拿着时间戳正常调用 OA API 接口 -> 获得 df_converted (如 17 条新数据)

# 3. 核心改动：彻底抛弃 pyiceberg，无脑 INSERT 追加进 RisingWave 物理表
with conn.cursor() as cur:
    for index, row in df_converted.iterrows():
        cur.execute("""
            INSERT INTO source_todo_table (task_id, task_empId, sync_time, status)
            VALUES (%s, %s, %s, %s)
            ON CONFLICT (task_id) DO UPDATE SET 
                task_empId = EXCLUDED.task_empId,
                sync_time = EXCLUDED.sync_time,
                status = EXCLUDED.status;
        """, (row['task_id'], row['task_empId'], row['sync_time'], row['status']))
    conn.commit()
conn.close()
print("✅ 增量数据已成功盲插追加进 RisingWave，Python 端耗时约 20 毫秒！")
```

> 请谨慎使用此类代码。

### 2. 【查询端】下游查询逻辑重构（DuckDB / BI 看板对接）

彻底终结 PyIceberg 每次耗时 8.6 秒的全表物理文件搬运。查询直接直连 RisingWave 的去重视图，由于最新去重数据天天活在流数据库的内存中，查询达到极致的秒开：

```python
import duckdb

# 下游 DuckDB 或者是 Python 分析端，不再查 OSS，直接查 RisingWave 的物化视图
con = duckdb.connect()
con.execute("INSTALL postgres; LOAD postgres;")

# 1. 连接 RisingWave 存储引擎
con.execute("ATTACH 'host=your_risingwave_host port=4566 dbname=dev user=root' AS rw (TYPE postgres);")

# 2. 直接无脑 SELECT * 查晓东建好的干净视图，不需要再跑繁重的窗口函数算去重
df_clean = con.execute("SELECT * FROM rw.mv_interface_clean_view WHERE task_empId = '103400';").df()

# 🚀 整个过程不需要发生任何全表 Parquet 下载，耗时只需 10 毫秒（0.01秒）！
print("🎉 极致秒开！最新去重数据在 10 毫秒内完全就绪。")
```

# 为什么需要开放表格式

## 核心矛盾：存储层只有"文件"，没有"表"

OSS/HDFS 这类存储只提供最原始的文件操作：

```
put / get / list / delete
```

它**完全不理解"表"的概念**。而数据库意义上的"表"需要：事务、一致性、Schema 管理、版本控制……这些能力统统缺失。

**开放表格式的本质：在"一堆文件"之上加一层元数据，把数据库的表语义补回来。**

## 没有表格式时的痛点（Hive 时代的老大难）

假设订单表就是 OSS 上一堆 Parquet 文件，按 `dt=2024-01-01/` 目录分区：

### 痛点 1：并发读写不一致
```
任务A 正在写入新数据文件（写了一半）
任务B 同时来查询 → 读到不完整/不一致的数据 ❌
```
没有"提交"的概念，无法保证读者要么看到全部、要么看不到。

### 痛点 2：并发写互相覆盖
两个任务同时写同一分区，最后写完的把先写的**直接覆盖**，数据丢失。

### 痛点 3：删除/更新极其痛苦
要删除某用户的订单（合规要求）：
- 必须找到包含该记录的所有文件
- **重写整个文件甚至整个分区**
- 重写过程中查询方看到的数据忽多忽少

### 痛点 4：查询慢（对 OSS 尤其致命）
```
Hive 查询流程：LIST OSS 目录 → 获取分区列表 → 再 LIST 文件
```
OSS 的 LIST 请求是 **HTTP 调用，延迟 10ms+ 且有速率限制**。分区成千上万时，光列目录就要几十秒，还没开始读数据。

### 痛点 5：Schema 演化 = 推倒重来
加列、改列名，历史数据全部要重写，否则新旧数据对不上。

## 开放表格式补回了什么

| 能力 | 实现方式 |
|------|---------|
| **ACID 事务** | 写入时先写数据文件，最后**原子替换**元数据指针（快照提交），要么全成功要么全失败 |
| **读写隔离** | 读者锚定旧快照，写者提交新快照，互不干扰（MVCC 思想） |
| **Schema 演化** | 元数据记录列 ID，加列/改名只改元数据，**不动数据文件** |
| **时间旅行** | 保留历史快照，可查询过去任意时刻的数据 |
| **高效查询** | 用**元数据统计裁剪**替代昂贵的目录遍历 |
| **增量读取** | 读两次快照之间的变更，支持流式消费 |

为什么 Iceberg 查询只读必要元数据——因为元数据就是它的"表目录索引"，这是相对"裸奔"的 Hive 表最大的性能提升来源之一。

## 为什么强调"开放"？

| | 封闭格式（如早期数仓） | 开放表格式 |
|--|--|--|
| 存储格式 | 私有格式 | **开放的 Parquet/ORC** |
| 引擎支持 | 绑定特定引擎 | Spark/Flink/Trino/StarRocks 随便读 |
| 数据主权 | 被平台锁定 | 数据永远是自己的，随时迁移 |
| 存算分离 | 老架构耦合 | 天然支持分离，存储放 OSS 省钱 |

"开放" = **数据以任何工具都能读的格式存在**，表格式本身的规范也是开源的，不存在厂商锁定。

## 大图景：Lakehouse 架构

```
传统数仓:   语义好（事务/性能强）  但贵、封闭、存算耦合
数据湖:     便宜、开放             但只是"文件堆"，无表语义 = 数据沼泽
                    ↓
湖仓一体 = 湖存储(OSS) + 开放表格式 + 多引擎
          = 仓库级的表语义 + 湖的成本和开放性
```

## 一句话总结

> **对象存储只管存文件，不管数据对不对、新旧、能不能改。开放表格式就是给文件堆加上"数据库表"的完整语义（事务、一致性、演化、版本），同时保持格式开放不被锁定——这是湖仓一体架构的基石。**

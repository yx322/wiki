# B-Tree vs 红黑树

两种经典平衡树数据结构，分别针对内存和磁盘两种介质做了截然不同的优化。

## 核心对比

| 特性 | 红黑树 | B-Tree |
|------|--------|--------|
| **形态** | 内存里的"瘦高个" | 硬盘里的"矮胖子" |
| **设计目标** | 内存中快速查找 | 对抗磁盘 IO 的龟速 |
| **节点容量** | 每节点存 1 个元素 | 每节点打包海量数据 |
| **平衡方式** | "左小右大"规则 + 颜色旋转 | 宽节点压低树高 |
| **树高** | O(log n)，但常数较大 | 极低（通常 3-4 层就能存亿级数据） |
| **时间复杂度** | O(log n) | O(log n)，但 log 的底数极大 |
| **IO 次数** | N/A（全在内存） | 争取用最少 IO 次数找到数据 |
| **适用介质** | 内存 | 硬盘 / SSD |

## 为什么设计差异这么大

### 什么是磁盘 IO？

磁盘 IO 就是 CPU/内存跟硬盘之间读写数据的过程。"I" 是 Input（读），"O" 是 Output（写）。

每次磁盘 IO，操作系统要做这些事：
1. 发出读/写指令给磁盘控制器
2. 磁盘定位到目标位置
3. 把数据从磁盘搬到内存（或反过来）
4. 通知 CPU "搞定了"

这整个过程就叫**一次磁盘 IO**。

### 磁盘 IO 到底有多慢？

| 操作 | 耗时 | 对比 |
|------|------|------|
| CPU 访问 L1 缓存 | ~1 纳秒 | 基准 |
| 内存访问 | ~100 纳秒 | 比 L1 慢 100 倍 |
| NVMe SSD 读取 | ~10 微秒 | 比内存慢 100 倍 |
| SATA SSD 读取 | ~100 微秒 | 比内存慢 1000 倍 |
| 机械硬盘（HDD）读取 | ~5-10 毫秒 | 比内存慢 **5 万到 10 万倍** |

换算成人类感知：如果内存访问是 1 秒，那机械硬盘 IO 就是 **5-10 天**。

### 为什么磁盘 IO 这么慢？

三个物理瓶颈：

**1. 寻道时间（HDD 独有）**：机械硬盘靠磁头物理移动到目标磁道，就像唱片机换歌——物理移动，不可能快。

**2. 旋转延迟（HDD 独有）**：盘片在转，磁头要等目标扇区转到自己下面才能读。7200 转的硬盘平均要等 4ms。

**3. 数据传输本身**：就算 SSD 没有机械部件，数据从闪存芯片搬到内存也要走总线、过控制器、穿过 PCIe 通道——每一步都有物理延迟。

**关键：每次 IO 不管读 1 个字节还是 16KB，"启动成本"差不多。** 就像叫外卖——不管点 1 个包子还是 10 个菜，配送费和时间是一样的。

### 为什么 B-Tree 要"矮胖"？

红黑树在内存里很爽，但放磁盘上就是灾难。假设要在 10 亿条数据里找一个 key：

**红黑树**：树高约 30 层 → **30 次磁盘 IO** → 30 × 5ms = **150 毫秒**

**B-Tree**：每个节点塞 1000 个 key（磁盘一次 IO 反正要读一整个页 4KB~16KB），树被压扁：

```
红黑树（瘦高）：          B-Tree（矮胖）：
    *                       [1000 keys]
   / \                    /    |    \
  *   *              [1000] [1000] [1000]
 / \ / \             /|\  /|\  /|\  /|\
*  * *  *         [1000]......[1000]  (1000个子节点)
...30层               3 层就够了
```

10 亿数据，B-Tree 只要 **3 层**：
- 第 1 层：1 个节点（根），1000 个 key → 1000 个子节点指针
- 第 2 层：1000 个节点，每个 1000 个 key → 100 万个子节点指针
- 第 3 层：100 万个叶子节点，每个存 1000 条数据 = **10 亿条**

3 次磁盘 IO × 5ms = **15 毫秒**，比红黑树快 10 倍。而且第 1 层（根节点）几乎永远在内存缓存里，实际只要 **2 次磁盘 IO = 10 毫秒**。

### 本质总结

> **磁盘 IO 的"启动成本"固定，所以每次 IO 尽量多搬数据。B-Tree 的"矮胖"就是利用这个特性：节点越大 → 树越矮 → IO 次数越少 → 越快。**

- 红黑树 = "每次只拿 1 个，但跑得飞快"（内存纳秒级，不在乎多跑几趟）
- B-Tree = "每次搬一车，尽量少跑"（磁盘毫秒级，能少一趟是一趟）

## 与 LSM-Tree 的关系

在 [[sql-vs-kv-pipeline]] 的讨论中，PostgreSQL 用 B-Tree 索引（每个节点一次磁盘 IO），而 [[fjall]]/[[slatedb]] 用 LSM-Tree（顺序写 + 内存 MemTable + 后台 Compaction）。LSM-Tree 牺牲了读性能（可能需要查多层 SSTable），换来了写入性能的极大提升——适合写密集场景。

| 存储结构 | 读性能 | 写性能 | 适用场景 |
|---------|--------|--------|---------|
| B-Tree | 快（直接定位） | 慢（随机写 + 页分裂） | 读多写少（传统数据库） |
| LSM-Tree | 较慢（多层查找） | 快（顺序追加） | 写多读少（Agent 记忆、日志） |
| 红黑树 | 极快（内存） | 快（内存） | 内存索引、Map 实现 |

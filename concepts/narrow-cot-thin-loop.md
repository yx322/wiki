# 窄 CoT 与薄循环工具试错

同一个设计哲学的两半：**窄 CoT 管模型"脑子里想什么"，薄循环 + 工具试错管"模型外怎么干活"**。这是 [[llm-overthinking]] 思考管理光谱上"可控思维流"档的具体工程形态。

## 窄 CoT：把思考限定在"有用的那一小段"

[[llm-overthinking]] 光谱上的三档：

```
[ 纯执行流 ] ── [ 可控思维流 ] ── [ 深度推理流 ]
100% 直球输出    认知载荷动态短路    无止境脑内博弈
                      ↑
              窄思维链（MiMo 2.5）
              约束在工具链拆解 + 边界检查
```

"窄"的定义：**思维链只允许覆盖两类内容——

1. **工具链拆解**：这个任务需要调哪些工具、按什么顺序、传什么参数
2. **边界检查**：参数合法吗、结果符合预期吗、有没有越界

就这么窄。不允许出现的是：对问题本身的长篇复述、对多种可能方案的反复权衡、对"我理解得对不对"的元思考、无病呻吟的自我怀疑。**

为什么窄是优点而不是缺陷——同一个任务两种 CoT 的输出对比：

```
深度推理流（宽）：
"用户想查库存。首先我要理解什么是库存……库存管理是 ERP 系统的核心功能之一，
历史上经历了从手工台账到信息化的演变……我应该考虑几种方案：方案 A 直接查询，
方案 B 先看分类再查询，方案 C 询问用户更多细节……让我权衡一下 A 和 B 的
优劣……A 的优点是……B 的优点是……嗯，其实还是要再确认用户的真实意图……"
（800 token，结论：该调 query_db 工具）

窄 CoT：
"需求：查商品库存。商品名含模糊词'6200'，需 LIKE 匹配。表 tbl_products，
只读权限。先查主件，有滤毒盒配件需联动查询。"
（60 token，动作：调 query_db）
```

两个输出**导向完全相同的下一个动作**（调 query_db），但窄的版本快 10 倍、便宜 10 倍、还不会在权衡中引入多余的犹豫。窄 CoT 砍掉的全部是"不改变下一步动作的 token"——这就是"认知载荷动态短路"：该想的一步不少（工具链拆解、边界检查是每一环都要的），不该想的立即短路。

实现上窄 CoT 有三种来源：

1. **模型训练侧**：MiMo 2.5 这类模型在 RL 阶段就用"约束在工具链拆解+边界检查"的奖励信号训练，思考天然长不歪
2. **模型侧开关**：skillforge 对 qwen 默认 `enable_thinking=False`——最窄的窄 CoT 是零 CoT，思考全部外化给循环
3. **提示词侧**：system prompt 里明确"不要复述任务、不要展开方案对比，直接给出工具调用"——不依赖模型的通用兜底

## 薄循环 + 工具试错：思考外化的执行侧

"薄"是相对于 LangGraph 那种厚框架说的。薄循环 = **while + 工具回填**（skillforge 的 130 行内核）：

```
while True:
    响应 = LLM(messages, tools)      # 模型决定调什么工具
    if 无工具调用: return 响应         # 想清楚了，答案就是不用工具
    结果 = 执行工具(...)              # 环境给出真实反馈
    messages += [工具结果]            # 反馈喂回去
```

"工具试错"的**试**字是核心：模型不确定时**不猜，发起一次真实调用，让环境告诉它对不对**。查库存不确定表名？先调 `list_tables`。SQL 不确定对不对？跑了才知道。这和 CoT 的脑内推演是本质不同的两种"思考"：

| | 脑内 CoT | 工具试错 |
|---|---|---|
| 反馈来源 | 模型自己对每步的评估（概率性） | 环境的真实输出（确定性） |
| 错误代价 | 错误会滚雪球（错前提继续推） | 错了立刻暴露，下一轮修正 |
| 成本 | token 费 + 无产出 | 一次真实调用（有产出） |
| 上限 | 受限于参数里的知识 | 知识在环境里，无限 |

[[llm-overthinking]] 里那句话的完整含义：**LSP、编译器、测试运行器是 100% 确定性的真实物理评估引擎**——工具试错的每一轮拿到的都是"物理世界的判决"，而 CoT 每一轮拿到的都是"模型的想象"。

## 为什么是"窄 CoT **加** 薄循环"而不是二选一

单用任何一个都有缺口：

**只有宽 CoT、没有工具**：模型在脑内模拟一切——模拟数据库查询结果、模拟代码执行输出，模拟得再像也是编的。

**只有薄循环、没有 CoT**：模型每轮裸奔着决定调什么工具，复杂任务（多工具编排、参数间有依赖）的第一步就容易选错，错了靠下一轮纠——工具调用轮数暴涨，延迟和费用反而更高。**窄 CoT 恰好补的就是"调工具前那一小段编排思考"**：60 token 想清楚"先查主件、再联动配件、要 LIKE 匹配"，比裸奔省两三轮试错。

拼起来的完整形态：

```
窄 CoT（脑内，60 token）：
   "查 6200 库存 → LIKE 匹配 → 先主件后配件"
        ↓
薄循环第 1 圈：调 list_tables → 真实返回表结构
        ↓
窄 CoT（10 token）："tbl_products 存在，字段 name/stock/price"
        ↓
薄循环第 2 圈：调 query_db("SELECT ... LIKE '%6200%'") → 真实数据
        ↓
窄 CoT（15 token）："主件命中 2 行，需查配件表联动"
        ↓
薄循环第 3 圈：调 query_db(配件联动查询) → 真实数据
        ↓
无工具调用 → 终局输出报价单
```

**脑内的每一小段思考都在为下一圈工具调用服务，每一圈工具的真实反馈都在修正脑内的计划。** 思考不再是一次性的长独白，而是散布在循环里的微型导航。

## 对应到两套系统

**skillforge**：现状即此形态。窄 CoT 靠三件事保证——qwen 默认关 thinking（最窄）、skill 提示词里 "EXECUTION OVER READING"（禁止读源码先执行，把试错推向工具侧）、`max_tool_steps=20` 且只数 `run_skill_script`（试错预算花在真实调用上）。展示层的 `enable_cot` 只是把脑内那一小段转发给前端看。

**Claude Code / Hermes**：interleaved thinking 是"窄 CoT + 薄循环"的成熟商用版——短 think 穿插在工具调用之间（上面 60→10→15 token 的节奏），而不是一次性长独白。它 think 频繁但每段很短，因为长 think 都花在**有环境反馈闭环**的任务上，且 think 完立刻用工具验证——不是纯脑内博弈。

## CoT 的缺点与局限性（补充：机制层）

窄 CoT 之所以要窄，机制层有四个先天缺陷（无法靠更多思考修复）：

1. **CoT 不等于真实计算——是"计算的表演"**：每一步仍是 next-token 采样，多位数乘法写得头头是道照样算错。精确计算必须外包工具
2. **错误滚雪球**：中间某步错了，后续全部建立在错误前提上，且模型倾向于将错就错；人类"觉得不对"的回头检查是元认知，模型的自我纠错是概率性的
3. **反事实盲区**：CoT 只能操作参数里已有的知识。事实检索、最新信息、需要环境反馈的验证——瓶颈在信息不在推理，思考是空转
4. **先定结论后辩护**：RL 训练的推理模型常见"结论在思考早期已定，长篇推演是 rationalization"——选项次序、措辞暗示都会影响"深思熟虑"的结果

工程层的代价：延迟（TTFT 全额支付）、成本（隐藏 token 计费）、上下文挤占与思维污染（长 think 污染后续轮次，触发连锁过度反思）、过度思考（简单问题上 token 翻倍正确率不提）、抗干扰差（长上下文下 CoT 质量崩塌）、思考泄露风险（CoT 可能复述系统提示词和敏感数据——`enable_cot` 网关是安全阀门）、假可解释性（CoT 是生成的文本不是决策日志，不能当审计依据）。

**有效/无效的判据**：CoT 有效的本质 = 推理链每一步都能被模型已有知识检验、且检验结果会改变最终答案；无效的本质 = 瓶颈在信息获取而非推理。前者是"想"的领地，后者是"查"的领地——Agent 循环的价值就是把两者编排起来：**该想的想（CoT），该查的查（工具），想完必查（验证）。**

# 开放表格式四大核心能力

[[why-open-table-format]] 的展开：开放表格式用元数据 + 快照机制，在对象存储上重新实现"数据库表"的四大核心语义。

## 1️⃣ 事务 — 要么全成，要么全败

### 是什么
把一组操作捆绑成一个**不可分割的工作单元**：里面的操作要么**全部成功**，要么**全部失败回滚**，不存在"做了一半"的中间状态。

### 经典例子：转账
```
A 账户扣 100 元
B 账户加 100 元
```
如果扣款成功后系统崩了，加款没执行 → 100 元凭空消失 ❌

事务保证这两步是一个整体：**要么都发生，要么都不发生**。

### 在数据湖中为什么重要
```sql
-- 一次写入任务：向订单表写入 3 个分区的数据
INSERT INTO orders
SELECT ... FROM 分区1, 分区2, 分区3
```

**没有事务的后果**（Hive 时代真实存在）：
- 写完分区 1、2 后任务失败 → 表里只有一半数据，且下游**已经读到这半份数据**了
- ETL 定时任务失败后，下游报表出错，只能人工修复

**有事务**：
```
写分区1 ✅ → 写分区2 ✅ → 写分区3 ✅ → 原子提交 ✅ → 数据对外可见
                    ↘ 任一步失败 → 已写的文件对查询不可见，表还是老样子
```
> 💡 Iceberg 的实现：所有文件先写好，最后**一次原子操作**替换元数据指针指向新快照。切换指针成功=提交成功，这就是"原子性"的来源。

## 2️⃣ 一致性 — 数据不能"自相矛盾"

### 是什么
数据在任何时刻都必须满足**定义好的规则和完整性约束**，从一个合法状态变到另一个合法状态，不能出现"中间烂状态"。

### 和事务的区别（容易混淆）
- **事务**强调"操作过程"：要么全做要么不做
- **一致性**强调"结果状态"：做完之后数据必须合法、自洽

### 数据湖中的具体体现

**问题 1：读者看到脏数据**
```
写任务正在写第 800 个文件（共 1000 个）
下游查询任务恰好这时候跑 → 读到 800/1000 的"半成品数据"
→ 聚合结果错误，且每次查询结果都不一样 ❌
```

**问题 2：约束被破坏**
```
orders 表规定 order_id 唯一
两个并发任务都写入了同一个 order_id → 数据自相矛盾 ❌
```

**表格式如何保证一致性**：
| 手段 | 作用 |
|------|------|
| **快照隔离（MVCC）** | 读任务锚定某个快照版本，读到的是**完整且不变的**数据，写一半也看不见 |
| **乐观并发控制** | 两个写任务提交时冲突 → 只有一个成功，另一个重试，不会互相覆盖 |
| **元数据校验** | 提交时验证 schema 匹配、分区值合法，不合法直接拒绝 |

> 一句话：**任何时刻查询这张表，得到的都是某个完整、合法版本的数据**——哪怕背后正在并发写入。

## 3️⃣ Schema 管理 — 表结构的定义与演变

### 是什么
Schema = 表的**结构定义**：有哪些列、每列什么类型、是否可空、分区怎么划分。

管理 = 对这个定义的**创建、修改、演化**，且历史数据能平滑适配。

### 没有它有多惨（传统 Hive 表）

```
场景：orders 表要加一列 user_level

问题1：Hive 的 schema 和数据目录强绑定
  → 新旧文件列数不一致，读历史文件时列错位
  → 数据"串列"了：把 user_level 的值读进了 age 列 ❌

问题2：Hive 修改分区列名 = 灾难
  → 元数据里的分区目录名没变，数据"消失"了

问题3：改列名/列类型
  → 必须重写全部历史数据文件，TB 级数据推倒重来
```

### Iceberg 的解法：按"字段 ID"而不是"位置"对应

```
传统 Hive：按位置对应 → v1 文件 (id, name)
                        v2 表   (id, name, age)  → v1 文件读出 age 缺失或错位

Iceberg：按 ID 对应
  字段 id=1: user_id
  字段 id=2: name
  字段 id=3: age     ← 后来加的
```
每个数据文件记录自己 schema 的字段 ID 列表，读取时**按 ID 匹配列**，跟位置无关。

### 支持的演化操作（都不用重写数据）
| 操作 | 原理 |
|------|------|
| 加列 | 新列在旧文件中读为 NULL |
| 删列 | 元数据标记隐藏，文件里数据还在但不读 |
| 改列名 | 只改 ID → 名字的映射 |
| 改类型 | 安全类型之间提升（int → long） |
| 改分区方式 | 新数据按新分区写，旧分区原样保留，查询时两种都能裁剪 |

## 4️⃣ 版本控制 — 表的"Git"

### 是什么
表每次修改（写入/删除/变更）都会生成一个**新版本（快照 Snapshot）**，旧版本被保留，可以：
- 查看/查询历史任意时刻的表
- 回滚到之前的版本
- 对比两个版本之间的差异

### 类比 Git
```
Git                    Iceberg
─────────────────────────────────────
commit             →   Snapshot（快照）
HEAD 指针          →   当前快照 ID
git checkout       →   Time Travel（时间旅行查询）
git reset/revert   →   Rollback（回滚）
git diff           →   增量读取（两个快照间的变更）
```

### 实际用途

**① 时间旅行：查过去**
```sql
-- 查询表 2 小时前的状态
SELECT * FROM orders TIMESTAMP AS OF '2024-06-01 10:00:00';

-- 查询指定快照版本
SELECT * FROM orders VERSION AS OF 123456;
```
场景：下游任务读错数据要**复现当时现场**排查问题、审计"上月底这张表长什么样"。

**② 回滚：撤销错误写入**
```sql
-- 上游误写了脏数据？不用删数据，直接把指针指回旧快照
CALL iceberg_catalog.system.rollback_to_snapshot('db.orders', 123456);
-- 秒级完成，因为旧数据文件根本没被删
```

**③ 增量读取：流式消费**
```sql
-- 只读两个快照之间的"变化"
SELECT * FROM orders.changes;  -- Flink/Spark 流式消费表的变更
```

**④ 依赖旧快照的隔离性**：读者读的是快照 N，写者提交快照 N+1，互不干扰——这就是前面"一致性"的实现基础。

### 代价与维护
```
快照不是免费的：
  旧快照引用的旧数据文件不能删 → 存储膨胀

所以需要定期清理：
  expire_snapshots(...)  → 过期快照 + 删除不再被引用的数据文件
```

## 四者的关系：一个闭环

```
事务（操作原子性）
   ↓ 保证每次变更产生的是一个完整合法的新版本
一致性（状态合法性）
   ↓ 靠多版本机制实现读写隔离
版本控制（历史可追溯）
   ↓ 每个版本记录着自己的结构定义
Schema 管理（结构可演化）
   ↓ 演化操作本身也是一次事务，产生新版本
   ↺ 回到事务
```

| 能力 | 解决的问题 | 一句话 |
|------|-----------|--------|
| 事务 | 操作做一半 | **要么全成，要么没做** |
| 一致性 | 数据自相矛盾/读到脏数据 | **任何时刻读到的都合法完整** |
| Schema 管理 | 表结构变更推倒重来 | **结构随便改，数据不用动** |
| 版本控制 | 改错了无法撤销、无法追溯 | **表的 Git：可查历史、可回滚** |

> 这四个能力合起来，就是"一堆 OSS 文件"和"一张数据库级的表"之间的全部差距——开放表格式做的事，就是用元数据 + 快照机制把这套语义在对象存储上重新实现一遍。

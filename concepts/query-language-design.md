# 查询语言设计

以 SurrealDB 的 SurQL 为切入点，分析查询语言的设计哲学。**核心洞见独立于 SurrealDB 是否被采用**——关于"查询语言应该长什么样"的论证依然有效。

## SQL 的根本性缺陷

### 语言缺陷

| 缺陷 | 说明 |
|------|------|
| **语法/执行顺序相悖** | 书写 SELECT 在前，执行 FROM 在前。非线性书写在嵌套子查询时极大增加认知负担 |
| **三值逻辑（NULL）** | `1 = NULL` 结果是 NULL，`NULL = NULL` 也是 NULL。`NOT IN` 子查询含 NULL 时返回空结果 |

### 架构缺陷：缺乏组合性

SQL 没有控制流（循环、条件判断），无法在查询内组合逻辑。这是架构层面的根因，引发连锁灾难：

- **数据搬运**：无法在查询内组合逻辑 → 被迫把数据拉到应用层编排 → 不必要的网络往返
- **ORM 是数据领域的"Go 语言"**：通过阉割对底层关系模型的表达力，换取面向对象层面的虚假舒适感，最终把性能灾难留给运行期

## SurQL 的六大架构级解决方案

| 方案 | 说明 |
|------|------|
| **1. 计算下推** | 允许在数据库层直接编写复杂业务逻辑，减少网络往返 |
| **2. 原生可组合性** | 查询是**值**而非文本，`LET $x = SELECT ...` 变量直接管道传递 |
| **3. 多模型统一** | 记录间直接链接（`->knows->`），无需传统 JOIN |
| **4. 原生实时推送** | `LIVE SELECT` 通过 WebSocket 订阅数据变更，省去 Kafka/Redis Pub/Sub |
| **5. 反 ORM** | 分布式可扩展性 + 原生执行，弥合存储过程与 ORM 的鸿沟 |
| **6. 现代语法** | 泛 Rust 血统：let/管道/类型后置/表达式导向 |

## 四种数据交互参照系

| 维度 | SQL | DataFrame | SurQL | KV 键空间 |
|------|-----|-----------|-------|----------|
| **载体** | 字符串 | 方法链（计算图）| 一等公民值 | 复合键编码 |
| **组合性** | 无（CTE 是补丁）| 有（方法链分叉/合并）| 有（变量管道）| 无（访问路径设计期定死）|
| **控制流** | 无 | 无（纯声明式）| 有（图灵完备）| 无 |
| **类型安全** | 无（字符串注入）| 有（编译期）| 有（值传递）| 有（编译期键编解码）|
| **优化器** | 黑盒 | 可见计算图 | 开发者可显式规划 | 无（键前缀即路径）|
| **执行边界** | DB 内 | 进程内 | DB 内（计算下推）| 进程内（嵌入式零 RTT）|
| **通用性** | 无（DB 沙箱）| 任意宿主语言 | DB 沙箱 | 完全通用 |

**选择逻辑**：
- **内部使用、查询模式固定** → 纯 KV（连封装都不需要）
- **内部灵活分析** → KV + DataFrame
- **外部/AdHoc/需求不可控** → SQL + 列式（DuckDB）或完整数据库

**网络 RTT 成本**：

| 存储 | RTT | 原因 |
|------|-----|------|
| KV（嵌入式）| **0** | 进程内直连，无网络 |
| SurrealDB | **1** | 计算下推，单请求完成 |
| PostgreSQL | **≈1** | CTE/单事务批量 |
| Redis | **N** | 多命令 N 次往返 |

## 关系建模对比

### 一对多：三种机制递进

| 机制 | 说明 | 适用 |
|------|------|------|
| **Record ID 指针** | `buyer = person:alice`，无需 JOIN | 简单一对多 |
| **图的边（RELATE）** | `RELATE alice ->bought-> iphone`，边可带属性 | 需要边属性（时间、权重）|
| **多态引用** | `liked_item` 可指向任意表 | 点赞商品/文章/评论 |

### 多对多：中间表的消亡

| 方案 | 物理结构 | 关系属性 | 查询复杂度 |
|------|---------|---------|-----------|
| SQL | 3 张表（实体+中间表）| 中间表加列 | 多次 JOIN，随跳数增长 |
| SurrealDB 图模式 | 2 点+1 边 | RELATE SET | 箭头穿透，一行代码 |
| SurrealDB 数组模式 | 2 张表 | 不支持 | `.*` 展开，极简 |

**⚠️ 僵尸指针**：数组模式下删除实体后，引用不会自动消失，需应用层清理。SQL 的 `ON DELETE CASCADE` 40 年前就解决了这个问题。

## SurrealDB vs PostgreSQL

| 层次 | 维度 | PostgreSQL | SurrealDB |
|------|------|-----------|-----------|
| **下限** | 性能 | 40 年优化器积累 | KV 引擎点查快 |
| **上限** | 语言设计 | SQL 缺乏组合性 | SurQL 碾压 |
| | 多态关联 | 笨重 | 碾压 |
| | 逻辑下沉 | ORM 补丁 | 碾压 |
| | RTT | 多次往返 | 碾压 |
| **生态** | 成熟度 | 碾压 | 新生 |
| | 数据一致性 | ACID+外键 | 需手动 event |
| | 云厂商 | 碾压 | 无 |

**判定**：四个范式维度 SurrealDB 碾压，四个生态维度 PG 碾压。互有胜负，没有全面碾压。SurrealDB 的正确定位不是"替代 PG"，而是"在 PG 做不到的维度上补充 PG"。
